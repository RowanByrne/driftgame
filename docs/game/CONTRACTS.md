# Contracts

Everything code relies on across modules and tasks: data, remotes, tags, attributes, paths and service APIs. Code against this doc. A change to it goes in the same commit as the code, and a change other tasks build on goes in first, as its own small commit (docs/workflow/CONDUCTOR.md "Main"). Analytics events have their own contract in `EVENT-CATALOG.md`. Replace each prompt with the answer.

## Remotes

> Every remote, named `<Feature><Action>` and created through `Shared/Net`. Every client-to-server remote lists the checks the server makes on it: types, ranges, rate limit.

| Name | Type | Direction | Owner | Payload and checks |
|---|---|---|---|---|
| `CarSpawn` | RemoteEvent | Server → client | `CarService` | `(car: Model, spawnCFrame: CFrame)`: the car this client drives, and where it starts |
| `CarState` | UnreliableRemoteEvent | Client → server | `CarService` | `(cf: CFrame, velocity: Vector3, drifting: boolean)` at 20 Hz. Server checks, in order: the player has a car the server has put somewhere; types; rate limit `StateRateLimit`/s per UserId; speed checked horizontal and vertical apart (**the top speed of the car that player is in** × `StateSpeedTolerance`, and `TerminalFall` × the same — the fall is the model's, gravity being the same for every car); the distance from where the server expects the car, with the budget since that position was agreed split the same way (`StateMoveTolerance`, plus `StateMoveAllowance` studs). A packet that fails is dropped and counted, not kicked, while this is a prototype — **and the next packet is checked against the same position**: a rejected packet never becomes the truth. For `RespawnGrace` after a respawn a packet that fails against the new position is also tried against the position the car was moved from, because a packet sent before the respawn can land after it; that one is passed on but does not move where the car is expected. For `CarSwitchGrace` after a car switch, a packet that fails against the **new car's** numbers is tried against the **old car's**, for the same reason — the packet was sent before the switch landed — and the ones that only the old car explains are counted in `switchInFlightKept`. Past that grace only the new car counts, so a switch to a slower car really does tighten the bound. **Not yet authoritative:** the server bounds speed and distance, it does not re-run the model. Before anything is scored or sold it must (`features/drift-model.md` "Open questions") |
| `CarRespawn` | RemoteEvent | Both ways | `CarService` | **Client → server:** `()`, a request, when the client's car has fallen below `Config.Drift.RespawnBelowY` or `DriftController:DebugReset()` is called. **No payload: the client cannot propose a position,** and anything sent is ignored. Server checks: the player has a live car (else ignored); rate limit `RespawnRateLimit` requests a second per UserId, the rest dropped and counted in `respawnsRefused`; at least `RespawnCooldown` seconds since that player's last respawn. A refused request gets no answer, and the client asks again after `RespawnAnswerWait`. **Server → client:** `(cf: CFrame)`, where the server has just put the car; the client restarts its simulation there. The client sends no `CarState` between asking and being answered |
| `CarSwitch` | RemoteEvent | Both ways | `CarService` | **Client → server:** `(key: string?)`, which archetype this client wants to be in (`Drift/DebugHud`, F4 or gamepad DPad right). **`nil` is a question, not a request** — "which car does the server have me in?" — which the client asks once at startup so it cannot miss the answer sent with its spawn. Server checks, in order: rate limit `CarSwitchRateLimit` asks a second per UserId, questions included, the rest refused and counted in `switchesRefused`; the key is a **string naming a known archetype** (`Cars.exists`) — a number, a table, the wrong case, a near miss and an unknown name are all refused, never trusted; the player has a live car. Accepted, the server records the car, re-dresses the car model (`CarModel.dress`, so the `Body` attribute and the new `Shell` replicate to everyone) and opens `CarSwitchGrace` on that player's `CarState` checks. Refused, nothing changes — no kick, no respawn, the car keeps its shape. **Server → client:** `(key: string, accepted: boolean)`, the car the server believes this player is in; sent with every spawn, after every ask, and after every refusal. The client may switch its own simulation the instant it asks, so the feel changes under a held finger, but this answer is what settles it: on `accepted = false` the client puts itself back in `key` |
| `CarStateOther` | UnreliableRemoteEvent | Server → client | `CarService` | `(userId: number, cf: CFrame, velocity: Vector3, drifting: boolean)`: another player's car, for drawing it |
| `GarageData` | RemoteEvent | Both ways | `GarageService` | The player's saved cars. **Client → server:** `()`, a request. **Server → client:** the garage. Rate-limited per UserId |
| `GarageSave` | RemoteEvent | Client → server | `GarageService` | `(name: string, car: { base: string, tune: { [string]: number } })`. The server validates the base against the archetypes and **every tuned number against `Shared/Cars/Garage`'s own ranges** — the same module the client drew the sliders from, which is why the two ends cannot disagree about what is legal. Rate-limited; a refusal changes nothing |
| `GarageDelete` | RemoteEvent | Client → server | `GarageService` | `(name: string)`. Rate-limited |
| `GarageTune` | RemoteEvent | Client → server | `GarageService` | `(car: { base, tune }?)`, what this player is driving right now, so the server can widen its own speed bound to match a tuned car instead of dropping its packets. Validated and rate-limited like the rest; `nil` is "back to the plain car" |

## Tags and attributes

> Every tag and attribute that other code reads. Studio-only attributes start with `__`.

| Tag or attribute | On | Set by | Used by |
|---|---|---|---|
| attr `__lync_port` | Workspace (Studio only) | Set by hand per place (docs/workflow/LANES.md) | Lync |
| attr `__test_profile` | Workspace (Studio only) | Set by hand in worker places | DataService (docs/workflow/TESTING.md) |
| attr `__agent_play` | Workspace (Studio only) | Agents, before each playtest | The quiet-playtest module (docs/workflow/TESTING.md) |
| attr `__studio_audio` | Workspace (Studio only) | Agents, for deliberate audio tests | The quiet-playtest module (docs/workflow/TESTING.md) |
| attr `Shell` | A car model | `Shared/CarModel.build`, when the car gets a body shell | `Drift/Render`, to know a shell is coming. A Model replicates before its parts, so a client that catches the car mid-replication must not decide there is no shell (T-016) |
| attr `N` | A `Shell` group (`Body`, `WheelFL`…`WheelRR`) | `Shared/CarModel` | `Drift/Render`: how many parts to wait for before the group counts as arrived |
| attr `L` | Every shell part | `Shared/CarModel` | `Drift/Render`: the part's CFrame inside its group. Render writes `groupCF * L` **absolutely** every frame — **never a pivot**. `Model:PivotTo` applies a *delta*, and the server re-asserts part CFrames, so each re-assertion was paid twice and the shell walked 2500 studs off the car inside a minute while its pivot tracked perfectly (T-020) |
| tag `DriftSurface` | Every part the car may drive on | `PlaygroundService`, when it builds the world; `TrackService`, when it adopts one; `Road/Builder`, on every road slab it makes | The drift model's ground rays filter to it. Buildings, pillars, cones and **the road's barriers** deliberately don't carry it: they are things to hit, not ground. The rays use an **include** list, so an untagged part is not low-grip ground — it is absent, and that is what makes a barrier a wall |
| attr `N`, `Kind`, `Variant` | A `Workspace.Road.Piece_<n>` folder | `Road/Builder` | Which piece of the run this is (`N`), which piece type (`Kind`: `Straight`, `Corner`) and which version of it (`Variant`: `Straight`, `CornerL`, `CornerR`). For reading the road off the Workspace in Studio; nothing in the game reads them back |
| attr `Surface` | A part tagged `DriftSurface` | Whoever builds the world | Which surface it is, for grip and score (`Config.Drift.GripTarmac` / `GripDirt`, `ScoreTarmac` / `ScoreDirt`). `"dirt"` is dirt; anything else, or absent, is tarmac. A solid the rays reach that is **not** tagged is "unspecified" and nearly frictionless (`GripUnspecified`) — except in a place where nothing at all carries the tag, where every solid is treated as road so a bare plate stays drivable |

## Paths

> Instance paths other code relies on, such as where the world is built, its named-spot markers (WORLD.md "Named spots"), or where a folder of models lives.

| Path | What's there | Made by |
|---|---|---|
| `ReplicatedStorage.Remotes` | Every remote | `Shared/Net`, on the server |
| `Workspace.Playground` | The prototype world: every surface, ramp and cone | `PlaygroundService` at `Init` (`Priority = 100`), before anything spawns into the world |
| `Workspace.Cars` | One model per player's car | `CarService` |
| `Workspace.Track` | A hand-placed track, when the place has one. Lives in the place file, never in git (AGENTS.md "Hand-built content"); the name is `Config.Drift.TrackName`. A place with one does not build the playground — both sit at the origin | Whoever placed it; adopted by `TrackService` |
| `Workspace.DriftTrajectory` | The projected-trajectory line while it is on, as a pool of reused anchored parts. Deliberately **not** inside `Workspace.Cars`, where the ground rays and the car-claiming logic would find it | `Drift/Trajectory` (client only) |
| `Workspace.Road` | The endless road's live window: one `Piece_<n>` folder per piece, plus one `ClosingBarrier` part. **Absent unless a run is going** — the road is off by default and `Generate(seed)` is what makes it, `Stop()` destroys the folder outright. The game's **third world**, at `Config.Road.Offset`, far from the track and the playground (`WORLD.md` "The three worlds") | `RoadService`, from `Shared/Road/Builder` |
