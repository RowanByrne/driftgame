# Contracts

Everything code relies on across modules and tasks: data, remotes, tags, attributes, paths and service APIs. Code against this doc. ## Remotes

> Every remote, named `<Feature><Action>` and created through `Shared/Net`. Every client-to-server remote lists the checks the server makes on it: types, ranges, rate limit.

| Name | Type | Direction | Owner | Payload and checks |
|---|---|---|---|---|
| `CarSpawn` | RemoteEvent | Server → client | `CarService` | `(car: Model, spawnCFrame: CFrame)`: the car this client drives, and where it starts |
| `CarState` | UnreliableRemoteEvent | Client → server | `CarService` | `(cf: CFrame, velocity: Vector3, drifting: boolean)` at 20 Hz. Server checks, in order: the player has a car the server has put somewhere; types; rate limit `StateRateLimit`/s per UserId; speed checked horizontal and vertical apart (**the top speed of the car that player is in** × `StateSpeedTolerance`, and `TerminalFall` × the same — the fall is the model's, gravity being the same for every car); the distance from where the server expects the car, with the budget since that position was agreed split the same way (`StateMoveTolerance`, plus `StateMoveAllowance` studs). A packet that fails is dropped and counted, not kicked, while this is a prototype — **and the next packet is checked against the same position**: a rejected packet never becomes the truth. For `RespawnGrace` after a respawn a packet that fails against the new position is also tried against the position the car was moved from, because a packet sent before the respawn can land after it; that one is passed on but does not move where the car is expected. For `CarSwitchGrace` after a car switch, a packet that fails against the **new car's** numbers is tried against the **old car's**, for the same reason — the packet was sent before the switch landed — and the ones that only the old car explains are counted in `switchInFlightKept`. Past that grace only the new car counts, so a switch to a slower car really does tighten the bound. **Not yet authoritative:** the server bounds speed and distance, it does not re-run the model. Before anything is scored or sold it must (`features/drift-model.md` "Open questions") |
| `CarRespawn` | RemoteEvent | Both ways | `CarService` | **Client → server:** `()`, a request, when the client's car has fallen more than `Config.Drift.FallBelowSurface` studs **below the last ground its wheels found** (`Drift/Model.fallFrom`), or `DriftController:DebugReset()` is called. **The test is relative, not a world height** (`T-067`): a descending road is not a fall, and on ground flat at Y = 0 it is the same comparison the old absolute `RespawnBelowY` made. That key no longer exists. **No payload: the client cannot propose a position,** and anything sent is ignored. Server checks: the player has a live car (else ignored); rate limit `RespawnRateLimit` requests a second per UserId, the rest dropped and counted in `respawnsRefused`; at least `RespawnCooldown` seconds since that player's last respawn. A refused request gets no answer, and the client asks again after `RespawnAnswerWait`. **Server → client:** `(cf: CFrame)`, where the server has just put the car; the client restarts its simulation there. The client sends no `CarState` between asking and being answered |
| `CarSwitch` | RemoteEvent | Both ways | `CarService` | **Client → server:** `(key: string?)`, which archetype this client wants to be in (`Drift/DebugHud`, F4 or gamepad DPad right). **`nil` is a question, not a request** — "which car does the server have me in?" — which the client asks once at startup so it cannot miss the answer sent with its spawn. Server checks, in order: rate limit `CarSwitchRateLimit` asks a second per UserId, questions included, the rest refused and counted in `switchesRefused`; the key is a **string naming a known archetype** (`Cars.exists`) — a number, a table, the wrong case, a near miss and an unknown name are all refused, never trusted; the player has a live car. Accepted, the server records the car, re-dresses the car model (`CarModel.dress`, so the `Body` attribute and the new `Shell` replicate to everyone) and opens `CarSwitchGrace` on that player's `CarState` checks. Refused, nothing changes — no kick, no respawn, the car keeps its shape. **Server → client:** `(key: string, accepted: boolean)`, the car the server believes this player is in; sent with every spawn, after every ask, and after every refusal. The client may switch its own simulation the instant it asks, so the feel changes under a held finger, but this answer is what settles it: on `accepted = false` the client puts itself back in `key` |
| `TestTools` | RemoteEvent | Both ways | `PlaygroundService` | **Studio-and-testing only, and labelled as such on screen** (`features/test-hill.md`, `T-065`). **Client -> server:** one string, `"lift"` to put the car at the top of the playground hill or `"rails"` to toggle the road's barriers; `nil` is a question. Nothing else is read -- no position, no height, no piece -- and ten forged payloads moved the car 0 studs. Guarded by `Config.Drift.CarSwitchRateLimit` and `RespawnCooldown`, the same two the run button borrows. **Server -> client:** the tool state. The car is moved by `CarService:Place`, never by this. 
| `CarExit` | RemoteEvent | Both ways | `CarService` | Getting out (`features/car-v2.md`, `T-096`). **Client -> server:** `(cf: CFrame)`, where the client stopped its car when Get out was pressed (button, `F`, gamepad Y); it holds the car there and sends no `CarState` from then on. Server checks, in order: rate limit `Config.CarEntry.RateLimit` requests a second per UserId, getting in and out together (`rate`); the player has a car the server has put somewhere (`no car`); they are driving and not mid-way in or out (`not driving`); the last speed the server agreed to, across the ground, is at most `ExitSpeed` x `ExitSpeedTolerance` (`too fast`). Then `cf` is **believed only if it is a sane CFrame that follows from where the server last agreed the car was** (the same `CarService.fits` every `CarState` passes); otherwise the car parks at that agreed pose, and a 900-stud lie parks it 0 studs from the truth. Accepted, the server moves its copy of the car there, drops every `CarState` until the driver is back in (`parkedDropped`), opens the rig's `DoorR` if it has one, stands the avatar at the exit point (root unanchored, `Driver` cleared) and shuts the door. **Server -> client:** `(ok: boolean, cf: CFrame?, reason: string?)`: `true` with where the car is parked, sent at once; `false` with the reason, and the client drives on from where it held |
| `CarEnter` | RemoteEvent | Both ways | `CarService` | Getting in (`T-096`). **Client -> server:** `(car: Model)`, the car to get into, from the Get in `ProximityPrompt` the owner's client hangs at its driver's door. Accepted: the door opens, the avatar is sat (root anchored, `Driver` set), the door shuts. **Server -> client:** `(ok: boolean, cf: CFrame?, reason: string?)`. `true` comes once the door is shut, with where the car is: drive from there, from rest. **The server also sends `true` unasked** whenever it sits a player who was out back in outright -- a respawn or `Place` (a run starting or ending), and a new avatar -- always before that respawn's own `CarRespawn` |
| `CarStateOther` | UnreliableRemoteEvent | Server → client | `CarService` | `(userId: number, cf: CFrame, velocity: Vector3, drifting: boolean)`: another player's car, for drawing it |
| `GarageData` | RemoteEvent | Both ways | `GarageService` | The player's saved cars. **Client → server:** `()`, a request. **Server → client:** the garage. Rate-limited per UserId |
| `GarageSave` | RemoteEvent | Client → server | `GarageService` | `(name: string, car: { base: string, tune: { [string]: number } })`. Rate-limited; a refusal changes nothing |

| `GarageTune` | RemoteEvent | Client → server | `GarageService` | `(car: { base, tune }?)`, what this player is driving right now, so the server can widen its own speed bound to match a tuned car instead of dropping its packets. | `RoadRun` | RemoteEvent | Both ways | `RoadService` | The start button (`Drift/RoadHud`, `features/endless-run.md`). **Client → server:** `(want: boolean?)` and nothing else — `true` starts a run, `false` ends it, **`nil` is a question** ("am I in a run?") which the HUD asks once at startup so a client that joined mid-run shows END and not START. **There is no position, no seed, no piece and no progress on this wire, and nowhere for one to hide:** anything that is not a boolean or nil is refused and counted, and extra arguments are never read — the handler takes one value. | `GarageVisit` | RemoteEvent | Both ways | `GarageVisitService` | The garage visit (`features/car-customization.md` "How it plays", `T-103`). **Client -> server:** `(want: boolean?)` and nothing else: `true` = take me in (the Garage HUD button, `G`, gamepad DPad down), `false` = drive me out (Drive out, gamepad Y), **`nil` is a question** ("am I in?"), asked once at startup. **No position, no part, nothing else is read.** Server checks, in order: rate limit `Config.GarageMenu.RateLimit` (4) asks a second per UserId, questions included (`rate`); the type (`bad ask`: a string, a number, a table, a Vector3 and an Instance were all refused). In: not in already (`already in`); at least `Cooldown` (1.5 s) since this player last left (`too soon`); not in a run, by `RoadService:InRun` (`in a run`); the room and its turntable exist (`no garage`); `CarService:Hold` takes the car: they have one (`no car`) and are driving, not mid-way in or out (`not driving`). Accepted in: the car is held on the turntable (`TurntableTop` raised by `RideHeight`, at the deck's current angle) and turns with it. Accepted out: the car is released at `CarExit` raised by `RideHeight`, facing out, at rest. **Server -> client:** `(state: { inGarage: boolean, ok: boolean, reason: string?, cf: CFrame?, rel: CFrame?, home: CFrame?, how: "door" \| "button"?, calledOff: string? })` after every answered ask, on every way in and out, and when a respawn, a `Place` or a new car calls the visit off (`calledOff`). In: `cf` is where the car is parked, `rel` its pivot relative to the turntable's pivot, `home` the turntable's pivot at angle 0, so a client draws its car on the deck it can see (`Turntable:GetPivot() * rel`). Out: `cf` is where to drive from |

## The car rig

> Car v2 (`features/car-v2.md`, T-094). How a car with moving parts is put together, replacing "a `Body` and four `Wheel*`" for any car built this way. **No car is built on it yet**: the user is importing a new model (2026-11-10), and it drops in by being assembled through `Shared/Cars/Rig.assemble` -- its meshes placed in the car's frame, plus a table naming each moving group, its kind and its pivot -- then dressed onto a car with `CarModel.dress`. `RigTests` proves the architecture on a synthetic rig of boxes.

The five simulation parts (`Body`, `WheelFL`…`WheelRR`, at `wheelOffsets()`) are unchanged and still what the simulation, the camera and the tests find the car by. A v2 `Shell` holds a `Body` group and one `Model` group per moving thing, each part in it carrying `L` relative to the group's `Pivot`; every group describes itself in attributes (above). Every part anchored, no physics, no attachment (DECISIONS.md, 2026-11-03). Pivots, seat, exit and floor points are in the **car's frame**: origin `RideHeight` above the road, front -Z, right +X (`Rig.fromBlender` converts Blender's X-left, -Y-forward, Z-up axes).

**Kinds:** `body` (the static shell, leaning with the body roll), `hinge` (turns about `Axis` through `Pivot`, `Open` degrees at full travel), `hub` (a wheel's suspension hub on the unleaned road frame: moves up and down by the wheel's lift, steers if `Steer` is set), `spin` (a wheel on its hub, spins about the car's X), `fixed` (rides its `On` group: a caliper on its hub), `aim` (turns about its pivot to point at `At`'s pivot: a strut's halves), `light` (a lamp, fixed on its `On` group).

**Names the game itself drives** -- any other group a model has is moved only by name through `CarParts`:

| Group | Kind | Rides on | Who moves it |
|---|---|---|---|
| `Body` | body | the car (leaning) | `Render`, with the car |
| `HubFL` `HubFR` `HubRL` `HubRR` | hub | the car's road frame | `Render`: the wheel's lift (`Render.setWheelLift`), and the steering on a hub with `Steer`. May hold no parts |
| `WheelFL` `WheelFR` `WheelRL` `WheelRR` | spin | `Hub<corner>` | `Render`: the wheels' spin |
| `CaliperFL` … `CaliperRR` | fixed | `Hub<corner>` | Steer with the hub, never spin |
| `DoorR` | hinge | body | The driver's door (right-hand drive): getting in and out, the next steps |
| `Hood`, then `HoodProp` | hinge | body | `CarParts.SEQUENCES.Hood`: the hood lifts, then the rod swings up; shut in the reverse order |

## Customization

> The garage's parts and paint (`features/car-customization.md`, T-101). The catalog, a built car, the one remote, and the attributes every client draws a car from. **Nothing here changes how a car drives yet:** `Customization.resolve` says what a build implies, and applying it is T-106.

**The catalog** (`Shared/Customization/Catalog.luau`, data only; frozen once loaded). Seven categories in menu order: `Engine`, `Suspension`, `Wheels`, `BodyKit`, `Underglow`, `Interior` hold one part each; `Paint` is four choices. Each part category is `{ id, label, kind, keys, parts }`: `kind` is `performance` (perf only), `both` or `looks` (look only), `keys` the tuner car keys its parts may move — **each key owned by one category**, so one build can move a key by at most `MaxDelta` (0.15). Each part is `{ id, name, category, perf?, look?, price, unlock }`:

- `id` unique across the catalog and never reused (the store keeps it); the stock part's id ends `_stock` and is listed first.
- `perf` = `{ [car key] = fraction }` on the tuner's car keys (`Shared/Cars/Garage` "the sliders"), each non-zero and within ±`MaxDelta`.
- `look`, by category (`LookFields`): Suspension `{ rideHeight (studs, -0.5..0.5, drawn only), stiffness (× the v2 suspension's Stiffness, 0.7..1.5) }`; Wheels `{ rim, tyre }` (model names); BodyKit and Interior `{ slots = { [slot] = piece name } }`; Underglow `{ colour: Color3, mode: "off" | "steady" | "pulse" }`. Stock carries no perf and no look.
- `price` (0) and `unlock` (`"free"`): present and unused until meta progression is decided.
- **Slots** a look may fill, as rig groups the drawing steps add to the car (`kind = fixed`, on the body): `KitFront`, `KitRear`, `KitSkirts`, `KitSpoiler`, `KitFlares`; `InteriorCage`, `InteriorSeat`, `InteriorWheel`, `InteriorAudio`.
- **Paint:** `colours` (`stock` plus a palette, each with `colour: Color3`), `finishes` (`stock`, `gloss`, `matte`, `metallic`, each with `material` and `reflectance`), `wraps` (`none` plus generic patterns, never a real brand). Fields `body` and `second` choose from `colours`, `finish` from `finishes`, `wrap` from `wraps`. `stock` means "the body's own", so the stock car recolours nothing.

**A built car:** `{ base: string, parts: { [categoryId] = partId }, paint = { body, second, finish, wrap } }`, every part category and paint field present. `base` is the archetype the server had the player in at their last fit (`CarService:CarKey`). Saved in **`DriftGarageDev_v1 / garage_<userId>`** as a new optional key `build` beside `cars`: `{ version = 1, at, cars, build? }`. Absent (every garage saved before T-101, and every player who never fitted anything) reads as the stock car; a stored build is passed through `Customization.sanitize`, so an unknown part or colour becomes stock and the rest is kept. **Still the dev store, not the save system** (`features/car-tuner.md` "The store").
